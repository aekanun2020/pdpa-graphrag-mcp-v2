**สรุป: ในระดับคำตอบ สองรุ่นไม่ต่างกัน** ในรอบที่รันจนจบ agent อ้างมาตราตามแนวคำตอบได้เกือบครบทั้งสองรุ่น (`main` 31 จาก 32 branch 33 จาก 35) ความต่างที่พบคือ `main` รันไม่จบ 3 จาก 24 คำถาม เพราะการเรียก `search_pdpa` ครั้งแรกเกิน 120 วินาที ส่วน branch รันจบทั้ง 24 คำถาม สาเหตุของ timeout ยังไม่ได้พิสูจน์

รอบก่อนหน้าทั้งหมดวัดว่า "มาตราที่ควรได้อยู่ใน context หรือไม่" รอบนี้เป็นรอบแรกที่วัดจากคำตอบของ agent

## วิธีทดสอบ

**agent:** harness จาก `aekanun2020/SUT-AI-Chat-App-with-Fine-tuned-Harness-with-KM` (commit `36f62c9`) ใช้ `runtime.py` เดิมไม่แก้ ทำงาน 3 ขั้น คือ แปลงคำถามเป็น contract, สืบค้นด้วยเครื่องมือ MCP, อ่านซ้ำแล้วเรียบเรียงคำตอบ
harness เดิมเป็นงานวิเคราะห์ข้อมูลด้วย SQL จึงเขียนชุด PDPA ขึ้นใหม่สำหรับรอบนี้: prompt 4 ไฟล์, policy, hook และตัวอ่านซ้ำ ผลรอบนี้จึงเป็นผลของ runtime เดิมกับชุด PDPA ที่เขียนใหม่ ไม่ใช่ผลของ harness ที่ปรับแต่งไว้กับสนามอื่น

- โมเดล `deepseek/deepseek-v4.1-flash` ทั้ง 3 บทบาท ผู้ให้บริการ DeepInfra, seed 39, temperature 0
- เรียกโมเดลได้ไม่เกิน 20 ครั้งและเรียกเครื่องมือได้ไม่เกิน 24 ครั้งต่อคำถาม เพดานรอผลเครื่องมือ 120 วินาที
- hook บังคับว่าเลขมาตราทุกตัวในคำตอบต้องปรากฏในหลักฐานที่ผูกไว้ และข้อเรียกร้องเรื่องโทษต้องผูกกับหลักฐานที่แสดงบทกำหนดโทษ
- ตัวอ่านซ้ำเรียก `get_section_text` ใหม่กับทุกมาตราที่ร่างคำตอบอ้าง แล้วส่งตัวบทเต็มให้ขั้นเรียบเรียง
- prompt ไม่มีเลขมาตราหรือคำตอบของชุดทดสอบ และ agent ไม่เห็นแนวคำตอบ

**server สองรุ่น:** ต่างกันที่ `lightrag/retrieval.py` ไฟล์เดียว ใช้กราฟและ collection ใน Qdrant ชุดเดียวกัน

- `main`: server ที่เปิดอยู่ port 8100 (โค้ด `2d82c09`)
- branch: process ที่สองใน container เดียวกัน port 8101 ใช้ `retrieval.py` ของ branch (`a706abf`) ข้ามขั้นสร้าง index จึงอ่าน Qdrant อย่างเดียว ไม่ restart server เดิม และปิดแล้วหลังทดสอบ

**คำถาม:** 24 ข้อจากชุดเดิม กลุ่มละ 8 ข้อ รันข้อละครั้งต่อรุ่น รวม 48 รอบ สองรุ่นของข้อเดียวกันรันพร้อมกัน

## รอบที่รันไม่จบ

ทั้ง 3 รอบเป็นของ `main` และล้มแบบเดียวกัน: agent สั่ง `search_pdpa` เป็นครั้งแรก แล้ว server ไม่ตอบภายใน 120 วินาที harness จึงหยุดด้วย `TimeoutError` หลังเรียกโมเดลไป 2 ครั้ง ยังไม่มีหลักฐานใดถูกเก็บ

สาเหตุยังไม่ได้พิสูจน์ ข้อสังเกตที่เข้ากันได้:

- `search_pdpa` ของ `main` คืน keywords เฉลี่ย 24.8 คำต่อครั้ง สูงสุด 48 คำ ส่วน branch เฉลี่ย 13.5 สูงสุด 14 เพราะ prompt ของ branch จำกัดจำนวนไว้ การให้โมเดลสกัด keywords ยาวกว่าน่าจะใช้เวลานานกว่า
- ระหว่างทดสอบมี server สองตัวแย่ง CPU กันใน container เดียว แต่ branch อยู่ในสภาพเดียวกันและไม่ timeout เลย

ไม่ได้วัดเวลาของขั้นสกัด keywords โดยตรง จึงยังสรุปไม่ได้ว่า prompt เดิมเป็นเหตุ ต้องรันซ้ำ 3 ข้อนี้บน `main` หรือจับเวลาที่ server เพื่อยืนยัน

## ทำไมคำตอบไม่ต่างกันทั้งที่ context ต่างกัน

รอบ 4 ถึง 9 พบว่า `main` ไม่ส่ง ม.4 มาใน context ของ `search_pdpa` ครั้งเดียว (0 จาก 9) แต่รอบนี้ agent บน `main` อ้าง ม.4 ได้ทุกข้อที่รันจบ (6 จาก 6) เพราะ agent ไม่ได้ค้นครั้งเดียว:

- ค้นซ้ำด้วยคำของตัวเอง เช่น R3 บน `main` ค้นครั้งที่สองด้วยคำว่า "ข้อยกเว้น กิจกรรมส่วนตัว ครัวเรือน" แล้วอ่าน ม.4
- อ่านตัวบทด้วย `get_section_text` และตามเส้นเชื่อมด้วย `get_related_sections` ซึ่งไม่ผ่าน `retrieval.py` สองรุ่นจึงตอบเหมือนกัน
- prompt ของขั้นสืบค้นสั่งให้ตรวจว่ากฎหมายใช้บังคับกับกรณีนั้นหรือไม่ก่อนสรุป

เนื้อหาคำตอบของกลุ่ม ม.4 ที่รันจบทั้งสองรุ่นไปทางเดียวกัน เช่น H1 (แอบบันทึกเสียงเก็บไว้ฟังเอง) ทั้งสองรุ่นตอบว่าไม่ผิดตาม ม.4 (1) และ H2 (ศาลเผยแพร่คำพิพากษา) ทั้งสองรุ่นตอบว่าไม่ต้องขอความยินยอมตาม ม.4 (5) พร้อมตั้งข้อสังเกตเดียวกันว่าตัวบทไม่ได้เขียนคำว่าเผยแพร่คำพิพากษาไว้ตรง ๆ

## ข้อจำกัด

- รันข้อละครั้งต่อรุ่น โมเดลไม่คงที่แม้ตั้ง seed (รอบนำร่องให้ contract ต่างกันจากข้อมูลเข้าเดียวกัน) ผลต่างระดับ 1 ถึง 2 มาตราจึงแยกจากความแปรปรวนของโมเดลไม่ได้
- ยอดรวมการเรียกเครื่องมือของ branch สูงกว่าเพราะ `main` มี 3 รอบที่หยุดก่อนได้เรียก เมื่อเทียบเฉพาะ 21 ข้อที่จบทั้งสองรุ่น ภาระงานของ agent ใกล้กัน: เรียกเครื่องมือ `main` 215 ครั้ง branch 208 ครั้ง, เรียกโมเดล 146 กับ 148 ครั้ง, ค่า deepseek 0.181 กับ 0.188 USD ต่างกันที่ branch เรียก `search_pdpa` มากกว่า (57 กับ 48 ครั้ง)
- ไม่ได้ตรวจความถูกต้องทางกฎหมายของคำตอบทีละประโยค อ่านเฉพาะส่วนสรุปของกลุ่ม ม.4
- ชุด PDPA ของ harness เขียนขึ้นในวันเดียวกับที่ทดสอบ ผ่านการทดสอบแบบไม่เรียกโมเดล 20 ข้อและรอบนำร่อง 4 รอบ ยังไม่เคยถูกวัดกับชุดคำถามอื่น
- agent ตัวอื่นที่ค้นครั้งเดียวแล้วตอบ หรือไม่เรียก `get_section_text` จะพึ่ง context ของ `search_pdpa` มากกว่านี้ ผลรอบ 4 ถึง 10 ยังใช้ได้กับ agent แบบนั้น
