# ผลทดสอบรอบ 12 — ผู้เรียนที่เริ่มจาก zip ได้ผลเดียวกับผู้สอนหรือไม่ (14 พ.ย. 2569)

ต่อจาก [รอบ 11](2026-11-13-agent-test.md) รอบนี้ไม่ได้เทียบโค้ดสองรุ่น แต่ถามว่าคนที่ไม่เคยมีโค้ดและข้อมูลชุดนี้ ดาวน์โหลด zip ของ repo แล้วทำตาม README จะได้ผลเดียวกับเครื่องของผู้สอนหรือไม่

**สรุป: ในทุกส่วนที่ไม่ขึ้นกับ LLM ผู้เรียนได้ผลตรงกับผู้สอนทุกตัวอักษร** ทั้งเครื่องมือ 4 ตัวที่ไม่ใช้ LLM (289 จาก 289 ครั้ง) และการค้นเมื่อใช้ keywords ชุดเดียวกัน (65 จาก 65 ครั้ง) ส่วนที่ขึ้นกับ LLM ฝั่ง server คือ keywords จาก `gpt-oss-120b` ซึ่งตรงกันบางคำ (รันฝั่งละครั้งเดียว)

**ไฟล์ดิบของรอบนี้ไม่ได้เก็บไว้** โฟลเดอร์ทดสอบถูกลบหลังทดสอบเสร็จ เพราะมีไฟล์ `.env` ที่มี API key อยู่ด้วย ตัวเลขในรายงานนี้คัดจากผลที่พิมพ์ออกมาระหว่างการทดสอบ สคริปต์ที่ใช้อยู่ที่ `eval/learner/` (เขียนกลับจากข้อความเดิมของสคริปต์ที่รันจริง)

## วิธีทดสอบ

**เครื่อง:** Mac ชิป ARM เครื่องเดียวกับของผู้สอน Docker Desktop หน่วยความจำ 7.65 GB ดิสก์ 126 GB

**ชุดของผู้เรียน:**

- ดาวน์โหลด zip ของ `main` ที่ commit `4f0ab65` ด้วย `gh api repos/<owner>/<repo>/zipball/main` แตกลงโฟลเดอร์ว่าง
- `cp .env.example .env` ตาม README
- `docker compose build --no-cache` เพื่อไม่ใช้ layer ที่เครื่องผู้สอนมีอยู่ แล้ว `docker compose up -d`
- เพิ่มไฟล์ `docker-compose.override.yml` (สำเนาอยู่ที่ `eval/learner/`) เปลี่ยนชื่อ container เป็น `mcp-pdpa-rag-learner`, `qdrant-learner` และ port เป็น 8110, 6343 เพื่อไม่ชนกับ container ของผู้สอน เป็นจุดเดียวที่ต่างจากขั้นตอนใน README

**ชุดของผู้สอน:** container `mcp-pdpa-rag` ที่ port 8100 ซึ่ง build จาก `main` ที่ commit `4f0ab65` และ image มีไลบรารีชุดที่ build ไว้ตั้งแต่ 10 พ.ย. กับผลที่บันทึกไว้ในรอบ 11 (`eval/agent/runs/runs.tar.gz`)

**ลำดับการรัน:** Docker 7.65 GB รันโมเดล BGE-M3 สองชุดพร้อมกันไม่ได้ จึงเก็บผลของฝั่งผู้สอนก่อน หยุด server ของผู้สอนด้วย `docker stop` รันฝั่งผู้เรียน แล้วเปิด server ของผู้สอนกลับด้วย `docker start` หลังเปิดกลับทุกครั้งตรวจเครื่องมือ 4 ตัวกับ 96 มาตราแล้วได้ผลตรงกับก่อนหยุด

## ระยะที่ 1 — ส่วนที่ไม่ขึ้นกับ LLM

ไม่ใช้ API key และไม่เรียก LLM เลย `.env` ของผู้เรียนยังเป็นค่าตัวอย่าง (server เริ่มได้โดยไม่ใช้ key)

| รายการ | ผล |
|---|---|
| ไฟล์ใน zip เทียบกับ `main` (`4f0ab65`) | ตรงกัน 216 จาก 216 ไฟล์ |
| สิทธิ์ execute ของ `examples/mcp_curl.sh` หลังแตก zip | ยังอยู่ |
| แพ็กเกจ Python ใน image (`pip list`) | ตรงกัน 116 จาก 116 |
| Python / สถาปัตยกรรม | 3.11.18 / aarch64 ทั้งสองฝั่ง |
| Qdrant | 1.20.0 ทั้งสองฝั่ง |
| log ตอนเริ่ม server | 190 nodes, 380 edges, 570 profiles, 96 chunks ทั้งสองฝั่ง |
| เครื่องมือ 4 ตัวที่ไม่ใช้ LLM กับ `sec_1` ถึง `sec_96` ผู้เรียนเทียบผู้สอน | ตรงกัน 289 จาก 289 ครั้ง |
| เครื่องมือกลุ่มเดียวกัน server ผู้สอนตอนนี้เทียบกับผลที่บันทึกในรอบ 11 | ตรงกัน 202 จาก 202 รายการที่เทียบได้ |
| การค้นแบบตรึง keywords ผู้เรียนเทียบกับ context ที่บันทึกในรอบ 11 | ตรงกัน 65 จาก 65 ครั้ง |

**เครื่องมือ 4 ตัว:** `get_pdpa_summary` 1 ครั้ง และ `get_section_text`, `get_related_sections`, `get_penalty` กับทุกมาตรา 96 มาตรา รวม 289 ครั้ง เรียกผ่าน MCP ของ server จริง เทียบข้อความที่ได้ทีละตัวอักษร (`eval/learner/tools_dump.py`)

**การค้นแบบตรึง keywords:** ดึงการเรียก `search_pdpa` ทุกครั้งของรอบ 11 ฝั่ง branch ที่มี keywords บันทึกไว้ ได้ 65 ครั้งจาก 24 คำถาม (`top_k` 5, 6 และ 8) แต่ละครั้งมีคำค้น keywords ที่ LLM ให้ในวันนั้น และ context ที่ server ส่งกลับ (`eval/learner/extract_kw.py`) จากนั้นใน container ของผู้เรียนให้ `retrieve()` ใช้ keywords ชุดนั้นแทนการเรียก LLM แล้วเทียบ context กับที่บันทึกไว้ทีละตัวอักษร (`eval/learner/fixed_kw_learner.py`) สคริปต์สร้าง index ด้วย `PDPALightRAG.build()` แบบเดียวกับที่ server ทำตอนเริ่ม ใน Qdrant ของผู้เรียนเอง

ผลนี้บอกสองอย่าง อย่างแรก ผู้เรียนที่ได้ keywords เดียวกับผู้สอนจะได้ context เดียวกัน อย่างที่สอง การแก้โค้ดเมื่อ 14 พ.ย. (ลบโค้ดที่ไม่ถูกเรียก เปลี่ยนชื่อตัวแปรโมเดล) ไม่เปลี่ยนผลค้น เพราะโค้ดที่ `4f0ab65` ให้ context ตรงกับที่บันทึกไว้ก่อนแก้

## ระยะที่ 2 — ส่วนที่ขึ้นกับ LLM

ทำตามหัวข้อ "เริ่มใช้งาน" ของ README ต่อจากจุดที่ใส่ key แล้ว รันสคริปต์ `./examples/mcp_curl.sh` กับ server สองฝั่ง ฝั่งละครั้งเดียว

- server ใช้ `gpt-oss-120b` ผ่าน OpenRouter สกัด keywords (ค่า `LLM_MODEL` ใน `.env.example`)
- key เป็นของผู้สอน ผู้สอนเป็นผู้ให้ key สำหรับการทดสอบนี้

### `./examples/mcp_curl.sh`

| รายการ | ผล |
|---|---|
| `tools/list` | ตรงกัน ได้เครื่องมือ 5 ตัว |
| `get_penalty(sec_26)` | ตรงกันทุกตัวอักษร (โทษ 2 รายการ ผ่าน `sec_79`) |
| keywords ระดับ low จาก `search_pdpa` | 8 คำทั้งสองฝั่ง ตรงกัน 7 คำ |
| keywords ระดับ high จาก `search_pdpa` | 6 คำทั้งสองฝั่ง ตรงกัน 2 คำ |

คำถามในสคริปต์คือ "เก็บข้อมูลสุขภาพพนักงานได้ไหม" ฝั่งผู้สอนได้ "มาตรา 27" ในระดับ low ส่วนฝั่งผู้เรียนได้ "ผู้ควบคุมข้อมูล" แทน ระดับ high ต่างกันที่ถ้อยคำเป็นหลัก เช่น "การให้ความยินยอม" กับ "ความยินยอม" และ "ข้อยกเว้นการใช้บังคับ" กับ "ข้อยกเว้นการบังคับใช้"

## การตรึงรุ่นหลังการทดสอบ

ตอนทดสอบ `requirements.txt` กำหนดแค่รุ่นขั้นต่ำ และ compose ใช้ `qdrant/qdrant:latest` การ build ใหม่ในวันที่ 14 พ.ย. ได้ชุดเดียวกับของผู้สอนเพราะยังไม่มีรุ่นใหม่กว่าออกมา หลังการทดสอบจึงตรึงรุ่นไว้ใน `requirements.txt`, `constraints.txt`, `Dockerfile` (Python 3.11.18) และ compose (Qdrant 1.20.0)

| การตรวจ | ผล |
|---|---|
| ตัวคำนวณของ pip (`pip install --dry-run --ignore-installed`) จากไฟล์ตรึงรุ่น | เลือก 114 แพ็กเกจ ตรงกับ image ที่ทดสอบทุกตัว (ไม่นับ `pip` และ `wheel`) |
| รัน `Dockerfile` จริงแบบไม่ใช้ cache จนจบขั้นติดตั้งไลบรารี จาก zip ที่ commit `34e7bd7` | ติดตั้ง 116 แพ็กเกจ ตรงกับ image ของผู้สอน 116 จาก 116 |

การ build ครบทั้ง 8 ขั้นจากไฟล์ตรึงรุ่นในรอบเดียวจนได้ image ทำสำเร็จในวันเดียวกัน จาก zip ที่ commit `9c62728` แบบไม่ใช้ cache: image ที่ได้มีแพ็กเกจตรงกับของผู้สอน 116 จาก 116 Qdrant รายงานรุ่น 1.20.0 และเครื่องมือ 4 ตัวที่ไม่ใช้ LLM ให้ผลตรงกับ server ของผู้สอน 289 จาก 289 ครั้ง ส่วนชุดของผู้เรียนที่ใช้ในระยะที่ 1 และ 2 build จาก zip ก่อนตรึงรุ่น ซึ่งมีไลบรารีชุดเดียวกับที่ตรึงไว้

## หน่วยความจำและดิสก์

- ตอนเริ่ม server (สร้าง index) ใช้หน่วยความจำสูงสุดที่สุ่มวัดได้ 4.66 GiB แล้วลดลงเหลือราว 2.8 ถึง 3.4 GiB ตอนทำงานปกติ
- เมื่อ Docker มี 7.65 GB และมี server อีกชุดรันอยู่ (ราว 3 GiB) การเริ่มชุดที่สองถูก kill ระหว่าง embed ตัวบท 96 chunks
- image ที่ build แล้วมีขนาด 17.9 GB ตามที่ Docker รายงาน (README เดิมเขียนว่าราว 5 GB)
- การ build แบบไม่ใช้ cache หนึ่งรอบใช้ดิสก์ของ Docker ราว 36 GB (build cache กับ image อย่างละราว 18 GB ประมาณจากผลต่างของ `docker system df` ก่อนและหลัง build)

README ถูกแก้ตามตัวเลขเหล่านี้แล้ว

## ข้อจำกัด

- ทดสอบบน Mac ชิป ARM เครื่องเดียว ซึ่งเป็นเครื่องเดียวกับของผู้สอน ไม่รู้ผลบน Windows, Linux หรือชิป Intel ค่า embedding อาจต่างเล็กน้อยบนฮาร์ดแวร์อื่น
- base image `python:3.11-slim` และ `qdrant/qdrant:latest` ใช้สำเนาที่มีในเครื่อง ไม่ได้ดึงใหม่จาก registry ผู้เรียนที่ดึงใหม่ในวันเดียวกันอาจได้ image คนละตัว หลังตรึงรุ่นแล้วความเสี่ยงนี้ลดลงแต่ไม่หมด เพราะ tag ยังชี้ไป image ใหม่ได้
- น้ำหนักของ BGE-M3 ดาวน์โหลดจาก Hugging Face ตอน build และไม่ได้ตรึง รุ่นที่ทดสอบคือ snapshot `5617a9f6`
- ชุดของผู้เรียนใช้ชื่อ container และ port ต่างจาก README
- การค้นแบบตรึง keywords เทียบกับผลที่บันทึกเมื่อ 13 พ.ย. ไม่ได้รันซ้ำบน server ของผู้สอนรุ่นปัจจุบัน เพราะหน่วยความจำไม่พอ
- ส่วนที่ขึ้นกับ LLM รันฝั่งละครั้งเดียว คำถามเดียว จึงแยกไม่ได้ว่าความต่างของ keywords มาจากเครื่องหรือจากความแกว่งของโมเดล (README ระบุไว้ว่าที่ temperature 0 คำถามเดียวกันยังได้ keywords มากกว่าหนึ่งชุด)
- ไฟล์ดิบถูกลบแล้ว ตรวจย้อนได้เฉพาะด้วยการรันซ้ำ
- repo เป็น private ผู้เรียนดาวน์โหลด zip ได้เมื่อได้รับสิทธิ์หรือได้รับไฟล์จากผู้สอน

## เหตุที่เกิดกับ server ของผู้สอนระหว่างทดสอบ

- restart 1 ครั้งโดยไม่ได้ตั้งใจ: process ทดสอบที่รันใน container ของผู้สอนโหลด BGE-M3 อีกชุดพร้อมกับที่ build ของผู้เรียนกำลังโหลดโมเดล หน่วยความจำไม่พอ container ถูก kill แล้ว restart เองตามนโยบาย `unless-stopped`
- หยุดชั่วคราว 2 ครั้งด้วย `docker stop` และ `docker start` เพื่อให้ชุดของผู้เรียนรันได้ ครั้งละราว 5 ถึง 6 นาที
- container `qdrant` ของผู้สอนไม่ถูกแตะตลอดการทดสอบ และไม่มีการใช้ `docker compose down`

- ระยะที่ 2: `gpt-oss-120b` 2 ครั้ง (สคริปต์ curl ฝั่งละ 1 ครั้ง) ไม่ได้เก็บตัวเลขเป็นเงิน
