# Q&A — ตรวจคำบรรยายคอร์ส GraphRAG (8–10 ก.ค. 2569) เทียบ paper

## Q1 — ลืมไปแล้วว่า profile คืออะไร ทำไมต้องมี

**Profile คือข้อความสั้น ๆ ที่เขียนแทนโหนดหรือเส้นแต่ละตัวในกราฟ เพื่อให้ vector search ค้นเจอโหนดนั้นได้** มันทำหน้าที่เป็นทางเข้าจากคำถามของผู้ใช้ไปสู่กราฟ

## ทำไมต้องมี

กราฟใน NetworkX ค้นได้แบบเดียวคือระบุ id ตรงตัว เช่น `sec_26` แต่ผู้ใช้ไม่ได้ถามด้วยเลขมาตรา ผู้ใช้ถามว่า "บริษัทเก็บลายนิ้วมือพนักงานได้ไหม" ซึ่งไม่มีคำไหนตรงกับ id ในกราฟเลย

ระบบจึงต้องมีขั้นแปลง "คำถามภาษาคน" ให้เป็น "โหนดตั้งต้นในกราฟ" และ profile คือสิ่งที่ทำให้ขั้นนี้เกิดขึ้นได้:

1. ตอนเริ่มระบบ สร้าง profile ให้ทุกโหนดและทุกเส้น (190 + 380 = 570 รายการ) แล้ว embed เก็บใน Qdrant collection `pdpa_profiles`
2. ตอนค้น นำคีย์เวิร์ดไปค้นใน `pdpa_profiles` ตามความหมาย
3. profile ที่ได้อันดับต้นบอกว่าโหนดไหนเกี่ยวข้อง แล้ว id ของ profile นั้นถูกใช้เป็น seed เพื่อเดินกราฟต่อ

อาจารย์อธิบายเหตุผลเดียวกันนี้ไว้เองในคลิป 9 ก.ค. 13.27 นาทีที่ 5:29–8:52 ว่า ถ้าผู้ใช้รู้เลขมาตราอยู่แล้วก็ไม่ต้องมี vector เลย แต่ผู้ใช้ไม่รู้ จึงต้องค้นด้วยความหมายก่อน

## หน้าตาของ profile

แต่ละ profile มี 3 ส่วน ตัวอย่างของโหนดนิยามข้อมูลชีวภาพ:

| ส่วน | หน้าที่ | ตัวอย่าง |
|---|---|---|
| `id` | ชี้กลับไปที่โหนดในกราฟ และใช้เป็น seed | `def_biometric` |
| `keys` | ข้อความที่ถูก embed คือสิ่งที่ถูกค้น | id, ประเภทโหนด, เนื้อหาไม่เกิน 200 ตัวอักษร, ชื่อความสัมพันธ์ |
| `value` | ข้อความที่ส่งออกไปใน context เมื่อค้นเจอ | "def_biometric (): ข้อมูลชีวภาพ: ข้อมูลส่วนบุคคลที่เกิดจากการใช้เทคนิค… ความสัมพันธ์: …" |

เหตุที่แยก `keys` กับ `value` คือสองส่วนนี้ทำงานคนละอย่าง `keys` ต้องสั้นและตรงประเด็นเพื่อให้ค้นแม่น ส่วน `value` ต้องอ่านรู้เรื่องเพื่อให้ agent เข้าใจ แนวคิดนี้มาจากขั้น profiling ของ LightRAG (§3.1)

## เทียบกับ chunk

ระบบมีสอง collection ที่ค้นคนละเป้าหมาย:

| | `pdpa_profiles` | `pdpa_chunks` |
|---|---|---|
| เก็บอะไร | ตัวแทนของโหนดและเส้นในกราฟ 570 รายการ | ตัวบทเต็ม 96 มาตรา |
| ค้นแล้วได้อะไร | จุดเริ่มต้นสำหรับเดินกราฟ | ข้อความกฎหมายไปให้ agent อ่าน |
| ตอบคำถามว่า | "ควรเริ่มเดินกราฟจากโหนดไหน" | "ตัวบทเขียนว่าอย่างไร" |

## กลับมาที่ประโยคในคู่มือ

ประโยคที่อาจารย์ยกมาหมายความว่า พอค้นเจอ profile ของ `def_biometric` ระบบหยิบ id นี้ไปเป็น seed ทันที ไม่มีขั้นที่ LLM อ่านผลค้นแล้วสกัดเลขมาตราออกมา และ seed ก็ไม่จำเป็นต้องเป็นมาตรา จะเป็นโหนดนิยาม ข้อยกเว้น หรือบทลงโทษก็ได้

# การค้นหนึ่งครั้งใน search_pdpa: ไล่จากคำถามจนถึง context

**คำถามที่ใช้:** "บริษัทเก็บลายนิ้วมือพนักงานเพื่อลงเวลาทำงาน ต้องขอความยินยอมไหม"

## สิ่งที่มีอยู่ก่อนเริ่มค้น

ตอน server เริ่มทำงาน ระบบเตรียมของไว้ 3 อย่าง:

**1. กราฟ** 190 โหนด 380 เส้น อยู่ในหน่วยความจำ

**2. Profile 570 รายการ** แบ่งเป็น 2 แบบ คือ profile ของโหนด 190 รายการ และ profile ของเส้น 380 รายการ ทุกรายการมี 3 ส่วนเหมือนกัน แต่ข้างในต่างกัน:

| ส่วน | profile ของโหนด (190 รายการ) | profile ของเส้น (380 รายการ) |
|---|---|---|
| `id` | id ของโหนดในกราฟ<br><br>ตัวอย่าง:<br>`def_biometric` | ประกอบจาก ต้นทาง + ชนิดเส้น + ปลายทาง คั่นด้วย `--`<br><br>ตัวอย่าง:<br>`sec_79--PRESCRIBES_PENALTY--pen_criminal_disclosure` |
| `KEYS` (ถูกแปลงเป็น vector) | id, ประเภทโหนด, เนื้อหาไม่เกิน 200 ตัวอักษร, ชื่อความสัมพันธ์ไม่เกิน 5 เส้น<br><br>ตัวอย่าง:<br>`"def_biometric"`<br>`"Definition"`<br>`"ข้อมูลชีวภาพ: ข้อมูลส่วนบุคคลที่เกิดจากการใช้เทคนิคหรือเทคโนโลยีที่เกี่ยวข้องกับการนำลักษณะเด่นทางกายภาพหรือทางพฤติกรรมของบุคคลมาใช้ทำให้สามารถยืนยันตัวตน"`<br>`"sec_26 DEFINES"`<br>`"IS_SUBTYPE_OF"` | ชนิดเส้น, id ต้นทาง, id ปลายทาง รวม 3 อย่างเท่านั้น<br><br>ตัวอย่าง:<br>`"PRESCRIBES_PENALTY"`<br>`"sec_79"`<br>`"pen_criminal_disclosure"` |
| `VALUE` (ส่งออกใน context) | id, เนื้อหาไม่เกิน 300 ตัวอักษร และรายการความสัมพันธ์ไม่เกิน 8 เส้น<br><br>ตัวอย่าง:<br>`def_biometric (): ข้อมูลชีวภาพ: ข้อมูลส่วนบุคคลที่เกิดจากการใช้เทคนิคหรือเทคโนโลยีที่เกี่ยวข้องกับการนำลักษณะเด่นทางกายภาพหรือทางพฤติกรรมของบุคคลมาใช้ทำให้สามารถยืนยันตัวตน`<br>`ความสัมพันธ์: sec_26 DEFINES; IS_SUBTYPE_OF: def_sensitive_data` | `ต้นทาง → [ชนิดเส้น] → ปลายทาง`<br><br>ตัวอย่าง:<br>`sec_79 → [PRESCRIBES_PENALTY] → pen_criminal_disclosure` |

วิธีอ่านตัวอย่างของโหนดเทียบกับคำอธิบาย:

| องค์ประกอบของ KEYS | ค่าในตัวอย่าง |
|---|---|
| id | `def_biometric` |
| ประเภทโหนด | `Definition` |
| เนื้อหาไม่เกิน 200 ตัวอักษร | `ข้อมูลชีวภาพ: ข้อมูลส่วนบุคคลที่เกิดจาก…ยืนยันตัวตน` |
| ชื่อความสัมพันธ์ | `sec_26 DEFINES` (เส้นขาเข้า มีต้นทางกำกับ) และ `IS_SUBTYPE_OF` (เส้นขาออก ไม่มีปลายทาง) |

โหนดนี้มีเส้นติดอยู่ 2 เส้น จึงมีชื่อความสัมพันธ์ 2 รายการ ไม่ถึงเพดาน 5 ส่วน `()` ที่ว่างอยู่หลัง id ใน VALUE คือช่องสำหรับ field `type` ของโหนด ซึ่งโหนดนิยามไม่มี โหนดที่มีค่านี้มีแค่โหนดบทลงโทษ 6 โหนด เช่น `pen_criminal_disclosure (อาญา): …`

Profile ของเส้นไม่มีเนื้อหาเลย เพราะเส้นทั้ง 380 เส้นในไฟล์กราฟมีแค่ต้นทาง ปลายทาง และชนิดเส้น ไม่มีคำอธิบาย KEYS ของเส้นจึงเป็น id ภาษาอังกฤษล้วน

**ส่วนไหนถูกค้น และส่วนไหนถูกส่งกลับ**

สิ่งที่ถูกค้นคือ KEYS ทั้งก้อน ไม่ใช่ id อย่างเดียว โค้ดนำสมาชิกทุกตัวใน KEYS มาต่อกันด้วยช่องว่างเป็นข้อความเดียว เช่น `def_biometric Definition ข้อมูลชีวภาพ: ข้อมูลส่วนบุคคล… sec_26 DEFINES IS_SUBTYPE_OF` แล้วแปลงข้อความนี้เป็น vector id เป็นสมาชิกตัวแรกของ KEYS จึงถูกค้นไปด้วยในฐานะส่วนหนึ่งของข้อความนี้

เมื่อค้นเจอ โค้ดได้ profile ทั้งรายการกลับมา ไม่ใช่แค่ VALUE แล้วนำแต่ละส่วนไปใช้คนละที่:

| ส่วนของ profile | ถูกนำไปใช้ที่ไหน |
|---|---|
| `id` | เป็น seed สำหรับเดินกราฟ (ขั้นที่ 3) |
| `VALUE` | เขียนลง context ส่งให้ agent (ขั้นที่ 6) |
| `KEYS` | ไม่ถูกใช้ต่อ หน้าที่ของมันจบที่การถูกค้น |

> **หมายเหตุ: อ่าน id อย่างไร**
>
> `sec_79` เป็น id ของโหนดมาตรา 79 ในกราฟ ส่วน id ของเส้นสร้างจากการนำ id ของโหนดสองตัวมาต่อกัน โดยมีชนิดเส้นอยู่ตรงกลางและคั่นด้วย `--` ตัวอย่าง `sec_79--PRESCRIBES_PENALTY--pen_criminal_disclosure` แยกได้เป็น 3 ส่วน:
>
> | ส่วน | ค่า | คืออะไร |
> |---|---|---|
> | ต้นทาง | `sec_79` | id ของโหนดมาตรา 79 (ประเภท Section) |
> | ชนิดเส้น | `PRESCRIBES_PENALTY` | ชื่อความสัมพันธ์ แปลว่า "กำหนดบทลงโทษ" |
> | ปลายทาง | `pen_criminal_disclosure` | id ของโหนดบทลงโทษ (ประเภท Penalty) ซึ่งมีเนื้อหาว่า "เปิดเผยข้อมูลส่วนบุคคลโดยมิชอบ: จำคุกไม่เกิน 6 เดือน / ปรับไม่เกิน 500,000 บาท" |
>
> อ่านรวมกันได้ว่า "มาตรา 79 กำหนดบทลงโทษทางอาญาเรื่องการเปิดเผยข้อมูลโดยมิชอบ"
>
> id ของโหนดใช้คำนำหน้าบอกประเภท:
>
> | คำนำหน้า | ประเภทโหนด | ตัวอย่าง |
> |---|---|---|
> | `sec_` | มาตรา | `sec_26`, `sec_79` |
> | `def_` | นิยาม | `def_biometric` |
> | `pen_` | บทลงโทษ | `pen_criminal_disclosure` |
> | `right_` | สิทธิ | `right_erasure` |
> | `lb_` | ฐานทางกฎหมาย | `lb_legal` |
> | `ch` | หมวดและส่วน | `ch2`, `ch2_p2` |
> | `secNN_ex` | ข้อยกเว้นของมาตรา | `sec24_ex6`, `sec26_ex5c` |
>
> เลขใน id ของมาตราเป็นเลขอารบิก แม้ตัวบทจะใช้เลขไทย `sec_79` จึงตรงกับ "มาตรา ๗๙"
>
> id ของเส้นไม่ได้ถูกเก็บไว้ในไฟล์กราฟ ไฟล์เก็บเส้นเป็น 3 ช่องแยกกันคือ `source`, `relationship`, `target` โค้ดนำสามช่องนี้มาต่อกันตอนสร้าง profile เพื่อให้ profile ของเส้นแต่ละตัวมีชื่อเรียกไม่ซ้ำกัน

**3. สอง collection ใน Qdrant**
- `pdpa_profiles` เก็บ vector ของ `KEYS` ทั้ง 570 รายการ รวมทั้งของโหนดและของเส้นไว้ด้วยกัน
- `pdpa_chunks` เก็บ vector ของตัวบทเต็ม 96 มาตรา

ทุกรายการใน Qdrant มี vector สองชนิด:
- **dense** เป็นตัวเลข 1024 ตัวที่แทนความหมาย ข้อความที่ความหมายใกล้กันจะได้คะแนนสูง แม้ใช้คำต่างกันหรือต่างภาษา
- **sparse** เป็นน้ำหนักของ token แต่ละตัว ให้คะแนนเฉพาะเมื่อคำค้นกับข้อความมี token เดียวกัน

การค้นทุกครั้งจึงค้นสองทางพร้อมกัน คือตามความหมาย (dense) และตามคำที่ตรงกัน (sparse)

## ขั้นที่ 1: LLM แตกคำถามเป็นคีย์เวิร์ดสองชุด

ขั้นนี้เป็นจุดเดียวที่เรียก LLM ผลที่ได้:

| ชุด | คีย์เวิร์ด |
|---|---|
| low-level (10 คำ) | ลายนิ้วมือ, ข้อมูลชีวภาพ, ข้อมูลอ่อนไหว, มาตรา ๒๔, มาตรา ๒๕, ความยินยอมโดยชัดแจ้ง, การเก็บข้อมูลเพื่อการทำงาน, PDPA, การประมวลผลข้อมูลส่วนบุคคล, ผู้ควบคุมข้อมูล |
| high-level (10 คำ) | consent, sensitive personal data, biometric data, purpose limitation, data controller obligations, employment monitoring, legal basis for processing, data subject rights, privacy principles, data protection compliance |

โค้ดนำคีย์เวิร์ดแต่ละชุดมาต่อกันด้วยช่องว่างเป็นข้อความเดียว ได้ **คำค้น 2 ข้อความ** คือข้อความ high-level (ภาษาอังกฤษล้วนในรอบนี้) และข้อความ low-level (ภาษาไทย) คำถามเดิมของผู้ใช้ไม่ถูกใช้ต่อจากจุดนี้

## ขั้นที่ 2: ค้น profile สองรอบ

โค้ดค้นใน `pdpa_profiles` สองรอบแยกกัน **รอบแรกใช้ high-level ขอ 5 รายการ รอบสองใช้ low-level ขอ 3 รายการ** ทั้งสองรอบค้นใน 570 รายการเดียวกัน ผลที่ได้จึงเป็น profile ของโหนดหรือของเส้นก็ได้ และสิ่งที่คำค้นถูกนำไปเทียบคือ vector ของ KEYS ตามที่อธิบายไว้ข้างบน

แต่ละรอบทำงานเหมือนกัน 3 ขั้นย่อย:
1. แปลงคำค้นเป็น dense vector และ sparse vector
2. ค้นฝั่ง dense และฝั่ง sparse แยกกัน ขอฝั่งละ 2 เท่าของจำนวนที่ต้องการ
3. รวมสองรายการด้วย RRF แล้วตัดเหลือจำนวนที่ต้องการ

**RRF** ให้คะแนนจากลำดับ ไม่ใช้คะแนนดิบ สูตรคือ คะแนน = 1 ÷ (60 + ลำดับฝั่ง dense) + 1 ÷ (60 + ลำดับฝั่ง sparse) โดยลำดับเริ่มนับจาก 0 และถ้ารายการไม่ติดฝั่งไหน ก็ไม่ได้คะแนนจากฝั่งนั้น

ค้นฝั่งละ 10 รายการ ผลรวมที่ได้:

| ลำดับผล | profile | ลำดับ dense | ลำดับ sparse | การคำนวณ | คะแนน |

| 5 | `def_personal_data` | 1 | ไม่ติด | 1/61 | 0.01639 |

ผมคำนวณตามสูตรแล้วตรงกับคะแนนที่ Qdrant คืนมาทุกแถว

สิ่งที่ตารางนี้บอก:
- **รายการที่ติดทั้งสองฝั่งชนะ** `sec24_ex6` ไม่ได้ที่ 1 ของฝั่งไหนเลย แต่ติดทั้งสองฝั่งจึงได้คะแนนรวมสูงสุด
- **อันดับ 3 กับ 4 คะแนนเท่ากันพอดี** ตัวหนึ่งเป็นที่ 1 ของฝั่ง sparse อีกตัวเป็นที่ 1 ของฝั่ง dense โค้ดตัดสินด้วยการเรียง id ตามตัวอักษร `def_biometric` จึงมาก่อน `def_data_controller`
- **ทั้ง 5 รายการเป็น profile ของโหนด** แต่มี profile ของเส้นเกือบติดอันดับ คือ `sec_26--DEFINES--def_biometric` ซึ่งอยู่ลำดับ 1 ของฝั่ง sparse และไม่ติดฝั่ง dense จึงได้คะแนน 1/61 = 0.01639 เท่ากับ `def_personal_data` ที่อยู่อันดับ 5 พอดี โค้ดตัดสินด้วยการเรียง id ตามตัวอักษรเช่นกัน id ที่ขึ้นต้นด้วย `def_` มาก่อน `sec_` profile ของเส้นตัวนี้จึงตกไปอยู่อันดับ 6 และถูกตัดออก ข้อนี้ผมคำนวณจากลำดับของสองฝั่งตามสูตร

**ทำไมแต่ละตัวติดฝั่ง sparse** (วัดจริงว่า token ไหนตรงกัน):

| profile | token ที่ตรงกัน | ที่มาของ token ใน KEYS |
|---|---|---|
| `def_biometric` | "metric" | มาจาก id `def_biometric` ซึ่งเป็นสมาชิกตัวแรกของ KEYS ตรงกับคำค้น "biometric data" |
| `sec24_ex6` | "consent" | มาจากเนื้อหา "…โดยไม่ต้อง consent…" |
| `sec24_ex2` | "consent" | มาจากเนื้อหาเช่นเดียวกัน |

คำค้นรอบนี้เป็นภาษาอังกฤษ ส่วน KEYS ของโหนดส่วนใหญ่เป็นภาษาไทย ฝั่ง sparse จึงตรงกันได้เฉพาะคำอังกฤษที่อยู่ใน KEYS คือ id ของโหนดและคำว่า consent

**ดังนั้น `def_biometric` ถูกค้นเจอเพราะ token ที่มาจากส่วน id ภายใน KEYS ไม่ใช่เพราะส่วนเนื้อหานิยามภายใน KEYS** ระบบยังคงค้นจาก KEYS ทั้งก้อนเหมือนเดิม เพียงแต่ในรอบนี้ส่วนที่ตรงกับคำค้นบังเอิญเป็นส่วน id และ `def_biometric` ไม่ติดฝั่ง dense เลย แปลว่ามันไม่ได้ถูกเจอด้วยความหมาย เหตุผลเดียวกันนี้ทำให้ profile ของเส้น `sec_26--DEFINES--def_biometric` ติดฝั่ง sparse ด้วย เพราะ KEYS ของมันมี id `def_biometric` อยู่

ส่วนฝั่ง dense จับความหมายข้ามภาษาได้ `def_data_controller` ได้ที่ 1 เพราะคำค้นมี "data controller obligations" ซึ่งความหมายตรงกับ "ผู้ควบคุมข้อมูลส่วนบุคคล" ใน KEYS

### รอบ B: ค้นด้วย low-level ขอ 3 รายการ

ค้นฝั่งละ 6 รายการ ผลรวมที่ได้:

| ลำดับผล | profile | ลำดับ dense | ลำดับ sparse | การคำนวณ | คะแนน |
|---|---|---|---|---|---|
| 1 | `sec_24` | 5 | 0 | 1/65 + 1/60 | 0.03205 |
| 2 | `def_sensitive_data` | 0 | ไม่ติด | 1/60 | 0.01667 |
| 3 | `def_personal_data` | 1 | ไม่ติด | 1/61 | 0.01639 |

`sec_24` ได้ที่ 1 ฝั่ง sparse เพราะมี token ตรงกับคำค้นหลายตัว ได้แก่ "๔", "ข้อมูล", "ควบคุม", "ยอม", "เก็บ", "มาตรา" โดย "๔" กับ "มาตรา" มาจากคีย์เวิร์ด "มาตรา ๒๔" ที่ LLM ใส่มาเอง

### รวมผลสองรอบ

โค้ดนำผลรอบ A ทั้ง 5 รายการขึ้นก่อน แล้วต่อท้ายด้วยผลรอบ B เฉพาะตัวที่ยังไม่มี `def_personal_data` ซ้ำจึงถูกทิ้ง ได้ 7 รายการ:

| อันดับในรายการรวม | profile | มาจากรอบ | คะแนนในรอบของตัวเอง |
|---|---|---|---|
| 1 | `sec24_ex6` | A (high-level) | 0.03200 |
| 2 | `sec24_ex2` | A (high-level) | 0.02920 |
| 3 | `def_biometric` | A (high-level) | 0.01667 |
| 4 | `def_data_controller` | A (high-level) | 0.01667 |
| 5 | `def_personal_data` | A (high-level) | 0.01639 |
| 6 | `sec_24` | B (low-level) | 0.03205 |
| 7 | `def_sensitive_data` | B (low-level) | 0.01667 |

**ลำดับนี้ไม่ได้เรียงตามคะแนนข้ามรอบ** `sec_24` ได้ 0.03205 ซึ่งสูงที่สุดในตาราง แต่อยู่อันดับ 6 เพราะมาจากรอบ B โค้ดวางผลของ high-level ไว้หน้าเสมอโดยไม่ดูคะแนน

คะแนนของสองรอบเทียบกันตรง ๆ ไม่ได้อยู่แล้ว เพราะ RRF ให้คะแนนจากลำดับภายในรอบของตัวเอง 0.03205 แปลว่า "ติดอันดับดีทั้งสองฝั่งในรอบ low-level" เท่านั้น

ในการค้นครั้งนี้ ทั้ง 7 รายการเป็น profile ของโหนด

## ขั้นที่ 3: เลือก seed

Seed ต้องเป็นโหนด เพราะเป็นจุดเริ่มเดินกราฟ โค้ดจึงไล่รายการ 7 ตัวตามลำดับในตารางข้างบน ข้ามทุกตัวที่ id มี `--` ซึ่งเป็น profile ของเส้น แล้วหยิบ 3 ตัวแรกที่เหลือ:

**Seed = `sec24_ex6`, `sec24_ex2`, `def_biometric`**

สิ่งที่ตามมาจากขั้นที่ 2:
- **Seed ทั้ง 3 ตัวมาจากรอบ A** เพราะรอบ A ให้มา 5 ตัวและทั้งหมดเป็นโหนด ผลของ low-level จึงไม่มีโอกาสเป็น seed ในการค้นครั้งนี้
- **`sec_24` ไม่ได้เป็น seed ทั้งที่คะแนนสูงสุด** เพราะอยู่อันดับ 6 ของรายการรวม ตามเหตุผลในหัวข้อก่อน มันกลับเข้ามาใน context ที่ขั้นที่ 4 เพราะเป็นเพื่อนบ้านของ seed `sec24_ex6` แต่นั่นเป็นผลของคำถามนี้ ไม่ใช่สิ่งที่โค้ดรับประกัน
- **ไม่มี LLM ในขั้นนี้** id ของ profile ถูกใช้เป็น seed โดยตรง
- **Seed ไม่จำเป็นต้องเป็นมาตรา** รอบนี้เป็นโหนดข้อยกเว้น 2 ตัวและโหนดนิยาม 1 ตัว

## ขั้นที่ 4: เดินกราฟจาก seed 2 hop

โค้ดเดินแบบ BFS คือสำรวจเพื่อนบ้านของ seed ให้ครบก่อน (hop 1) แล้วจึงสำรวจเพื่อนบ้านของเพื่อนบ้าน (hop 2) โดยเดินตามเส้นทั้งขาออกและขาเข้า

**Hop 1** ได้ 5 โหนด seed แต่ละตัวมีเส้นติดอยู่ 2 เส้น:

| โหนดที่ไปถึง | มาจาก seed | ผ่านเส้น |
|---|---|---|
| `lb_legal` | `sec24_ex6` | IS_LAWFUL_BASIS (ขาออก) |
| `sec_24` | `sec24_ex6` | GRANTS_EXEMPTION (ขาเข้า) |
| `lb_vital` | `sec24_ex2` | IS_LAWFUL_BASIS (ขาออก) |
| `def_sensitive_data` | `def_biometric` | IS_SUBTYPE_OF (ขาออก) |
| `sec_26` | `def_biometric` | DEFINES (ขาเข้า) |

`sec24_ex2` ก็มีเส้นไป `sec_24` แต่โหนดนี้ถูกไปถึงแล้วจาก `sec24_ex6` จึงไม่นับซ้ำ

**Hop 2** ได้อีก 36 โหนด รวมทั้งหมด 41 โหนด

**แต่ context รับได้แค่ 15 รายการแรก** ซึ่งเรียงตามลำดับที่เดินถึง คือ 5 โหนดของ hop 1 ตามด้วย 10 โหนดแรกของ hop 2 และ 10 โหนดนั้นเป็นเพื่อนบ้านของ `sec_24` ทั้งหมด: `lb_archive`, `lb_contract`, `lb_public_task`, `lb_legitimate`, `sec24_ex1`, `sec24_ex3`, `sec24_ex4`, `sec24_ex5`, `ch2`, `ch2_p2`

**ผลคือเพื่อนบ้านของ `sec_26` ไม่ได้เข้า context เลย** ทั้งที่ ม.26 เป็นมาตราที่ตรงกับลายนิ้วมือ เหตุผลคือ `sec_24` ถูกเดินถึงก่อน `sec_26` และ `sec_24` มีเพื่อนบ้านมากจนกินโควตา 15 รายการหมด ข้อยกเว้นของ ม.26 และมาตราโทษที่อ้างถึง ม.26 จึงถูกตัดทิ้ง ส่วนโหนดอย่าง `ch2` (หมวด 2) ที่แทบไม่ช่วยตอบคำถามกลับได้เข้าไป 15 รายการนี้ถูกเลือกด้วยลำดับการเดิน ไม่ได้เลือกด้วยความเกี่ยวข้อง

การออกแบบปัจจุบันให้ agent เป็นผู้ตามต่อเอง docstring ของ `search_pdpa` สั่งไว้ว่าหลังได้ผลแล้วให้เรียก `get_related_sections` กับมาตราที่พบ เมื่อ agent เห็น `sec_26` ใน context แล้วเรียกเครื่องมือนั้น ก็จะได้เพื่อนบ้านของ ม.26 ครบ ข้อมูลจึงไม่ได้หายถาวร แต่ต้องใช้การเรียกเพิ่มอีกหนึ่งรอบ

**รูปแบบของแต่ละรายการใน context**

```
[hop1][DEFINES] sec_26: มาตรา ๒๖ ห้ามมิให้เก็บรวบรวมข้อมูลส่วนบุคคลเกี่ยวกับเชื้อชาติ…
```

สิ่งที่ LLM ของ agent ใช้ได้จากบรรทัดนี้:

| ส่วน | LLM ใช้ทำอะไรได้ |
|---|---|
| `sec_26` | เป็นกุญแจสำหรับเรียกเครื่องมือต่อ เช่น `get_section_text('sec_26')`, `get_penalty('sec_26')` นี่คือประโยชน์หลัก |
| `DEFINES` | บอกว่าโหนดนี้เกี่ยวข้องในฐานะอะไร |
| `hop1` | บอกว่าอยู่ใกล้หรือไกลจากจุดเริ่ม |
| เนื้อหาไม่เกิน 200 ตัวอักษร | ให้ตัดสินได้ว่าคุ้มที่จะขอตัวบทเต็มหรือไม่ |

สิ่งที่บรรทัดนี้ไม่บอก คือ **เส้นนั้นโยงมาจากโหนดไหน และทิศไปทางใด** LLM เห็นว่า `sec_26` เข้ามาด้วยเส้น `DEFINES` แต่ไม่รู้ว่าอีกปลายของเส้นคือ `def_biometric` และไม่รู้ว่าใครนิยามใคร รายการ hop 2 เช่น `[hop2][GRANTS_EXEMPTION] sec24_ex1` ก็ไม่บอกว่ามาจาก `sec_24`

ผลคือ LLM รู้ว่าโหนดเหล่านี้เกี่ยวข้อง แต่ประกอบเส้นทางเองไม่ได้ เช่นสรุปจากบรรทัดเหล่านี้อย่างเดียวไม่ได้ว่า "ลายนิ้วมือเป็นข้อมูลชีวภาพ ซึ่งนิยามไว้ในมาตรา 26" ต้องอาศัยตัวบทจากขั้นที่ 5 หรือเรียกเครื่องมือเพิ่ม

ขั้นนี้อ่านโหนดและเส้นจากกราฟในหน่วยความจำโดยตรง ไม่ได้ใช้ profile อีก

## ขั้นที่ 5: ค้นตัวบทใน pdpa_chunks

ขั้นนี้ **ไม่ใช้ผลจากขั้นที่ 3 และ 4** โค้ดนำคีย์เวิร์ด low-level ต่อด้วย high-level เป็นข้อความเดียว แล้วค้นใน `pdpa_chunks` ขอ 5 มาตรา ด้วยวิธี dense + sparse + RRF แบบเดียวกับขั้นที่ 2 โดยค้นฝั่งละ 10 รายการ

| ลำดับผล | มาตรา | ลำดับ dense | ลำดับ sparse | การคำนวณ | คะแนน |
|---|---|---|---|---|---|
| 1 | มาตรา ๒๖ | 0 | 0 | 1/60 + 1/60 | 0.03333 |
| 2 | มาตรา ๒๔ | 1 | 2 | 1/61 + 1/62 | 0.03252 |
| 3 | มาตรา ๔๐ | 7 | 3 | 1/67 + 1/63 | 0.03080 |
| 4 | มาตรา ๒๓ | 6 | 9 | 1/66 + 1/69 | 0.02964 |
| 5 | มาตรา ๒๕ | ไม่ติด | 1 | 1/61 | 0.01639 |

มาตรา ๒๖ ได้ที่ 1 ทั้งสองฝั่ง จึงได้คะแนนเต็มที่สูตรนี้ให้ได้ ขั้นนี้คือจุดที่ทำให้ตัวบทของ ม.26 เข้า context แม้ขั้นที่ 4 จะตัดเพื่อนบ้านของ ม.26 ออกไป

**การค้นแยกจากกราฟแบบนี้มีทั้งข้อดีและข้อเสีย**

ข้อดี:
- **เป็นตาข่ายรองรับเมื่อ seed ออกมาไม่ดี** ในตัวอย่างนี้ seed สองในสามเป็นข้อยกเว้นของ ม.24 และกราฟตัดเพื่อนบ้านของ ม.26 ทิ้ง แต่ตัวบทเต็มของ ม.26 ยังเข้า context ได้เพราะขั้นนี้ค้นแยก ถ้าผูกขั้นนี้กับกราฟ ความผิดพลาดของ seed จะลามมาถึงตัวบทด้วย
- **คำค้นสองภาษาช่วยกันได้** ฝั่ง dense จับความหมายจากทั้งคำไทยและคำอังกฤษ

ข้อเสีย:
- **มาตราที่กราฟหาเจอไม่ได้ตัวบท** กราฟมีหน้าที่หามาตราที่เกี่ยวข้องแต่ข้อความไม่คล้ายคำถาม เช่นมาตราโทษ แต่เมื่อหาเจอแล้ว context ไม่มีตัวบทของมาตรานั้น agent ต้องเรียก `get_section_text` เองอีกรอบ
- **เลขมาตราที่ LLM เดาส่งผลต่อผลค้น** ม.25 ติดอันดับ 5 ด้วยฝั่ง sparse อย่างเดียว ซึ่งน่าจะมาจากคีย์เวิร์ด "มาตรา ๒๕" ที่ LLM ใส่มาเอง ข้อนี้อนุมานจากลำดับ ไม่ได้วัด token
- **คำถามเดิมของผู้ใช้ไม่ถูกใช้** คำค้นเป็นคีย์เวิร์ด 20 คำต่อกัน ความหมายของประโยคเดิม เช่น "เพื่อลงเวลาทำงาน" ถูกแตกเป็นคำ ๆ

## ขั้นที่ 6: ประกอบ context ส่งกลับให้ agent

Context ที่ส่งกลับยาว 14,056 ตัวอักษร ประกอบจาก 3 ส่วนตามลำดับ:

| ส่วน | มาจากขั้น | ปริมาณจริง | เพดานในโค้ด |
|---|---|---|---|
| VALUE ของ profile ที่ค้นเจอ | ขั้นที่ 2 | 7 รายการ | 8 |
| รายการที่ได้จากการเดินกราฟ | ขั้นที่ 4 | 15 รายการ | 15 |
| ตัวบทเต็มของมาตรา | ขั้นที่ 5 | 5 มาตรา (ม.26 ยาว 3,520 ตัวอักษร) | 5 |

ส่วนแรกรับ VALUE ของ profile ทั้งสองแบบ ถ้ามี profile ของเส้นติดอยู่ในรายการที่ค้นเจอ VALUE ของมันในรูป `ต้นทาง → [ชนิดเส้น] → ปลายทาง` จะถูกส่งให้ agent ด้วย แม้ profile ของเส้นจะเป็น seed ไม่ได้ ในการค้นครั้งนี้ไม่มีกรณีนั้น

Server หยุดที่นี่และไม่เขียนคำตอบ agent เป็นผู้อ่าน context แล้วตัดสินใจว่าจะเรียกเครื่องมือตัวอื่นต่อหรือตอบผู้ใช้

## Profile ทั้ง 7 ตัวที่ค้นเจอ

ทั้ง 7 ตัวเป็น profile ของโหนด

**`sec24_ex6`** (ข้อยกเว้น, รอบ A อันดับ 1, เป็น seed)

## สิ่งที่ Qdrant เก็บจริง

จุดของ `def_biometric` ใน `pdpa_profiles`:

| ส่วน | ค่าจริง |
|---|---|
| payload | `{"index": 121, "profile_id": "def_biometric", "node_category": "prebuilt"}` |
| dense vector | ตัวเลข 1024 ตัว |
| sparse vector | น้ำหนักของ 39 token |

Qdrant ไม่ได้เก็บ `KEYS` และ `VALUE` เป็นข้อความ เก็บแค่ vector ที่แปลงมาจาก `KEYS` กับเลข `index` เมื่อค้นเจอ โค้ดใช้เลข 121 ไปหยิบ profile ลำดับนั้นจากหน่วยความจำของ server จึงได้ `id` ไปเป็น seed และได้ `VALUE` ไปใส่ context วิธีนี้ใช้กับ profile ของเส้นเหมือนกัน

## ข้อจำกัดของโค้ดที่ตัวอย่างนี้เผยให้เห็น

| จุด | สิ่งที่เกิดในตัวอย่าง | ทางปรับที่เสนอ |
|---|---|---|
| การเลือก seed (ขั้นที่ 3) | ผลของ high-level อยู่หน้าเสมอ `sec_24` ที่ติดอันดับดีที่สุดของ low-level จึงไม่ได้เป็น seed | ให้ seed มาจากทั้งสองรอบ เช่นหยิบอันดับ 1 ของแต่ละรอบก่อน |
| โควตา 15 รายการ (ขั้นที่ 4) | เพื่อนบ้านของ `sec_24` กินโควตาหมด เพื่อนบ้านของ `sec_26` ถูกตัด | แบ่งโควตาต่อ seed และให้เส้นทางกฎหมาย เช่น `PRESCRIBES_PENALTY`, `GRANTS_EXEMPTION`, `REFERENCES_SECTION` มาก่อนเส้นโครงสร้างอย่าง `CONTAINS_SECTION` |
| รูปแบบบรรทัดใน context (ขั้นที่ 4) | ไม่บอกต้นทางและทิศของเส้น LLM ประกอบเส้นทางเองไม่ได้ | เขียนต้นทางและทิศลงไปด้วย เช่น `[hop1] def_biometric ←DEFINES— sec_26: …` |
| การค้น chunk (ขั้นที่ 5) | มาตราที่กราฟหาเจอไม่ได้ตัวบท และคำถามเดิมไม่ถูกใช้ | คงการค้นแยกไว้เป็นตาข่ายรองรับ แล้วเพิ่มคำถามเดิมในคำค้นฝั่ง dense และแนบตัวบทของมาตราที่เป็น seed หรืออยู่ hop 1 |

ทางปรับทั้ง 4 ข้อเป็นข้อเสนอ ยังไม่ได้แก้ในโค้ดและยังไม่ได้ทดลองว่าผลดีขึ้นจริง

## สรุปเส้นทางของการค้นครั้งนี้

1. คำถามถูกแตกเป็นคำค้น high-level (อังกฤษ) กับ low-level (ไทย)
2. แต่ละคำค้นถูกเทียบกับ vector ของ KEYS ทั้งสองทาง high-level ค้นได้ 5 profile ส่วน low-level ค้นได้ 3 และซ้ำ 1 จึงรวมเป็น 7 ทั้งหมดเป็น profile ของโหนด
3. seed คือ id ของโหนด 3 ตัวแรก ซึ่งมาจาก high-level ทั้งหมด
4. กราฟพาจาก `def_biometric` ไปถึง `sec_26` ได้ใน 1 hop แต่เพื่อนบ้านของ `sec_26` ถูกตัดออกเพราะโควตา 15 รายการเต็มด้วยเพื่อนบ้านของ `sec_24`
5. ตัวบทของ ม.26 เข้า context ได้จากการค้น chunk ซึ่งทำแยกต่างหาก
6. context 14,056 ตัวอักษร ซึ่งมี VALUE ของ profile รายการจากกราฟ และตัวบท ถูกส่งกลับให้ agent

## ที่มาของข้อมูล

- คีย์เวิร์ดชุดนี้มาจากการเรียก `search_pdpa` จริง จากนั้นผมนำคีย์เวิร์ดชุดเดียวกันไปรันฟังก์ชันของโค้ดทีละขั้นใน container เพื่อเก็บคะแนนและลำดับ context ที่ประกอบได้ยาว 14,056 ตัวอักษร เท่ากับของการเรียกจริง
- LLM แตกคีย์เวิร์ดไม่เหมือนกันทุกครั้ง ถ้าถามคำถามเดิมอีกรอบแล้วได้คีย์เวิร์ดชุดอื่น ตัวเลขทุกตารางในนี้จะเปลี่ยนตาม
- ตัวอย่างนี้ทำกับคำถามเดียว ข้อที่ว่า seed มาจาก high-level ทั้งหมดเป็นผลของการค้นครั้งนี้ ถ้ารอบ A มี profile ของเส้นติดอันดับ ผลของ low-level ก็มีโอกาสเป็น seed ได้

## จุดที่เพิ่มจากฉบับก่อน

1. **หัวข้อ "ส่วนไหนถูกค้น และส่วนไหนถูกส่งกลับ"** ในส่วนเตรียมการ พร้อมตารางว่า id, VALUE และ KEYS ถูกใช้ที่ไหน
2. **รอบ A** แก้ประโยคตัวหนาเรื่อง `def_biometric` ให้ชัดว่าค้นจาก KEYS ทั้งก้อน และ token ที่ตรงมาจากส่วน id
3. **รวมผลสองรอบ** เปลี่ยนรายการ 7 ตัวเป็นตารางที่มีรอบและคะแนน และ **ขั้นที่ 3** เพิ่มคำอธิบายว่าทำไม `sec_24` ไม่ได้เป็น seed
4. **ขั้นที่ 4** เพิ่มเรื่อง agent ตามต่อด้วย `get_related_sections` และหัวข้อย่อยว่ารูปแบบบรรทัดใน context ให้อะไรและขาดอะไร
5. **ขั้นที่ 5** เพิ่มข้อดีและข้อเสียของการค้น chunk แยกจากกราฟ
6. **หัวข้อใหม่ "ข้อจำกัดของโค้ดที่ตัวอย่างนี้เผยให้เห็น"** รวมทางปรับ 4 ข้อ
